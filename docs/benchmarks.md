# Exo vs Docker benchmarks

This document records the current Windows/WSL2 benchmark results for Exo vs
Docker Desktop. The numbers are generated by `scripts/bench-vs-docker.ps1` and
can be converted to Markdown with `scripts/bench-to-markdown.ps1`.

## Environment

- Host: Windows, PowerShell
- Docker path (default): Windows `docker.exe` -> Docker Desktop named pipe ->
  `docker-desktop` WSL2 engine
- Docker path (`-DockerViaWsl`): Windows PowerShell -> `wsl -e docker ...` ->
  Docker Desktop engine from inside WSL. This bypasses a flaky Windows named-pipe
  CLI path while still measuring Docker Desktop.
- Exo path: `exo.cmd` -> a single `wsl -u root -e .../target/release/exo`
  invocation in the `Ubuntu` WSL2 distro
- Timing: wall-clock, median of 20 runs unless noted
- Workload: short-lived container execution (`true`) and mounted-workspace
  existence checks

This is intentionally a Windows agent-runtime benchmark: it measures the user
experience of invoking containers from Windows, including Docker Desktop's daemon
and named-pipe path.

## Important fix: remove wrapper tax

Early results understated Exo because `exo.cmd` ran an extra `wsl -e bash` check
on every command before launching Exo. Removing that per-invocation check reduced
Windows Exo spawn latency dramatically:

| Path | Median | p95 | Max |
| --- | ---: | ---: | ---: |
| old `exo.cmd` wrapper | 344 ms | 402 ms | 469 ms |
| fixed `exo.cmd` wrapper | 121 ms | 155 ms | 166 ms |

The headline results below use the fixed wrapper.

## Cold pull (fixed wrapper, Docker via WSL)

Source files:

- `results/bench-windows-20260624-154800.json` - `alpine:3.20`
- `results/bench-windows-20260624-154829.json` - `busybox:latest`
- `results/bench-windows-20260624-154903.json` - `debian:bookworm-slim`
- Combined Markdown: `results/summary-cold-fixed-wsl-docker.md`

These runs used `-AllowColdDelete`, which removes the named image from both
runtimes first (`docker rmi -f` and `exo rmi`) and then times pull + first run.
They also used `-DockerViaWsl` because the Windows `docker.exe` named-pipe path
became intermittently unresponsive while Docker from inside WSL stayed healthy.

| Image | Docker cold pull | Exo cold pull | Result | Docker first run | Exo first run |
| --- | ---: | ---: | --- | ---: | ---: |
| `alpine:3.20` | 1829 ms | 1005 ms | Exo 45.1% faster | 454 ms | 138 ms |
| `busybox:latest` | 1840 ms | 852 ms | Exo 53.7% faster | 427 ms | 128 ms |
| `debian:bookworm-slim` | 4157 ms | 1488 ms | Exo 64.2% faster | 483 ms | 339 ms |

Takeaway: with the fixed wrapper, Exo cold pulls are about 1.8x-2.8x faster in
this run, and first-run-after-pull is also faster across all three images.

For comparison, the earlier conservative cold report recorded before the wrapper
fix is still available as `results/summary-cold.md`.

## Storage efficiency

Exo stores images in a content-addressed layer store (`~/.exo/layers/`). Each
layer is extracted once and shared across images via hardlinks. On hosts where
the kernel allows overlay mounts, Exo can mount the shared layer directories
directly as overlay `lowerdir`s, eliminating the per-image `rootfs/` copy
entirely. The disk-savings number therefore comes from two effects:

1. Cross-image layer deduplication (shared inodes).
2. Zero-copy overlay composition when layers are whiteout-free.

Run `exo system df` to see physical vs logical bytes and the dedup ratio.

## Reproduce

Warm spawn + volume + agent image benchmark:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/bench-vs-docker.ps1 `
  -Runs 20 -Image alpine:3.20 `
  -IncludeVolume -IncludeFirstRun -IncludeAgentImages -IncludeDaemon -EmitMarkdown
```

True cold pull benchmark (destructive only to the named image in both runtimes):

```powershell
powershell -ExecutionPolicy Bypass -File scripts/bench-vs-docker.ps1 `
  -Runs 20 -Image alpine:3.20 `
  -IncludeVolume -IncludeFirstRun -ColdImage alpine:3.20 `
  -AllowColdDelete -IncludeAgentImages -IncludeDaemon -EmitMarkdown
```

If Windows `docker.exe` is unresponsive but Docker works from inside WSL, use:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/bench-vs-docker.ps1 `
  -Runs 20 -Image alpine:3.20 -DockerViaWsl `
  -IncludeVolume -IncludeFirstRun -ColdImage alpine:3.20 `
  -AllowColdDelete -IncludeAgentImages -IncludeDaemon -EmitMarkdown
```

Combine JSON results into one Markdown report:

```powershell
$files = Get-ChildItem results/bench-windows-*.json | Select-Object -Expand FullName
& ./scripts/bench-to-markdown.ps1 -JsonPath $files -OutFile results/summary.md
```

Density benchmark (Linux/WSL2):

```bash
./scripts/bench-density.sh
```

With custom image, batch size, and ceiling:

```bash
IMAGE=busybox:latest BATCH=25 MAX=500 ./scripts/bench-density.sh
```

Convert density JSON to Markdown:

```powershell
& ./scripts/bench-to-markdown.ps1 `
  -JsonPath results/bench-density-*.json -OutFile results/summary-density.md
```

OpenClaw agent benchmark (Linux/WSL2, requires Docker):

```bash
./scripts/bench-openclaw.sh
```

Convert OpenClaw JSON to Markdown:

```powershell
& ./scripts/bench-to-markdown.ps1 `
  -JsonPath results/bench-openclaw-*.json -OutFile results/summary-openclaw.md
```

## Caveats

- Docker Desktop can become unresponsive even while its WSL2 distro is running;
  the benchmark script has a bounded health check to avoid multi-minute hangs.
- The comparison is Windows-centric by design. Docker includes Docker Desktop's
  daemon/named-pipe path; Exo uses a direct WSL invocation.
- The current Exo daemon path is not auto-started or stopped by the benchmark to
  avoid foreground hangs or killing runtime-owned processes. If a daemon is
  already running, the script records daemon metadata and can measure detached
  start.
- Cold-pull numbers above use `-DockerViaWsl` because Windows `docker.exe`
  became intermittently unresponsive; this is documented as part of the Docker
  Desktop user-experience path.
